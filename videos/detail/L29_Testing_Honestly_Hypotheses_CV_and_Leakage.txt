#0
Let me explain why this lecture matters. Everything we have done is exploration. At some point you must say whether your findings and your model will hold up on new data. Testing honestly means setting up the test so that it cannot flatter you. Many wrong results in data science come not from bad algorithms, but from tests that accidentally let information leak. Today we look at hypotheses, train and test, cross-validation and leakage, which together make a trustworthy workflow. The second lecture is about reporting what you found.
#1
Let me add how the two lectures fit together. In lecture twenty-nine, we make sure that the numbers are honest. In lecture thirty, we make sure that the story we tell with them is honest. The same dataset, Online Shoppers, is used for both, so you will see the same features and target again. By now you know that fifteen percent of visits end in a purchase, that page value is a very strong signal, and that duplicate rows exist, which will matter for leakage.
#2
Let me explain each step with an example from your own life. Suppose you believe that students who attend more classes score higher. That is a hunch. A specific version says that students with attendance above eighty percent score higher on the final than those below. A testable version names the comparison, say the mean marks of the two groups, and the test, say a t-test. The decision rule says that you will accept the idea if the p-value is below point oh five. Writing this before you run the test protects you from adjusting the question to fit the answer.
#3
Let me explain what the p-value means here. It is the probability of seeing a difference at least this large, if there were really no difference. A p-value near zero means such a difference would be extremely unlikely by chance. Notice also the size of the effect: fourteen times higher is a big effect, and a small p-value on a tiny effect would be less interesting. Both matter. Remember the first lecture, too. These hypotheses came from exploring this same data, so a stricter approach would test them on a held-out part, or on fresh data. We follow that idea in the train and test logic next.
#4
Let me explain how to do it in code. From sklearn dot model selection import train test split. Call it with X, y, test size point two, stratify equal to y, and a random state, for example forty-two. Never look at the test rows, never use them to choose features, scale values or tune settings. The test set is used once, at the end, to report the final score. If you use it many times to compare models, you are effectively training on it, and the score becomes optimistic. For tuning, use cross-validation inside the training rows, or a separate validation set.
#5
Let me explain how to do it. cross val score takes the model, the training data, the number of folds, and the scoring, for example roc auc. Use StratifiedKFold so that each fold has the same share of buyers. The mean tells you the expected score, and the standard deviation tells you how much it moves from fold to fold. If the spread is large compared to the difference between two models, you cannot say that one is better. Cross-validation also helps with small datasets, where a single split would be very noisy.
#6
Let me give an example of each type. Target leakage: predicting whether a loan will default, and including a column about collection calls, which only exist after the default. Contamination: the same customer appears in both train and test because of duplicates, so the model has seen the answer. Preprocessing leakage: computing the mean for filling missing values from the whole dataset, so the test rows influenced the training. Sampling leakage: copying rare rows before splitting. The common feature is that the test score is better than reality, and a very high score on a hard problem should make you suspicious.
#7
Let me explain how large this effect can be. The same data, the same model, the same metric, differ only in the order of two steps. When we over-sample first, copies of the same buyer land in both train and test, and the recall reaches point nine nine two, which looks perfect. When we split first and over-sample only the training rows, the recall is point six six five. The difference of more than thirty points is entirely leakage. A very high number is a reason to investigate before celebrating, and this is exactly why order of operations matters.
#8
Let me explain how to use a pipeline. In scikit-learn, make pipeline of StandardScaler and LogisticRegression ties the steps together. When you call cross val score on the pipeline, each fold fits the scaler on its own training part and applies it to its own validation part, so no information leaks. If you scaled the data first and then passed it to cross validation, the scaler would have used all the rows. The same applies to imputers, selectors and encoders. When in doubt, put it in a pipeline. And ask the question for every feature: would I know this at the time the prediction is made?
