#0
Let me explain why this module matters. Imagine a model with ninety-five percent accuracy built on data where borough names are spelled two ways and ten percent of rows are duplicated. The score looks good, but the model has learned the mistakes. Industry surveys often say that data scientists spend a large part of their time preparing data. So this module is not a side topic. It is where most real projects are won or lost. Today we cover the concepts, and the lab shows the code on a real merged file.
#1
Let me add an example of raw versus clean. A raw table of student records may have the same student twice, one with marks as text, one with a blank, and a branch spelled CSE, cse and Computer Science. A clean table has one row per student, marks as numbers, blanks explained, and one spelling. Notice the idea of one row per entity. If a student appears twice, any count of students, average of marks, or split between train and test data becomes wrong. Always audit first, because you cannot fix what you have not measured.
#2
Let me add a sentence for each. Accuracy is about truth, which needs an outside reference. Completeness is about presence, and about the reason for absence. Consistency is about sameness, one fact in one form. Validity is about rules, whether the value could possibly be right. A useful way to remember: accuracy asks is it true, completeness asks is it there, consistency asks is it the same everywhere, and validity asks is it allowed. A value can pass one test and fail another.
#3
Let me explain the peer median idea. If you do not have the true price, compare each listing with similar listings. Group by borough and room type, take the median price in each group, and look at the ratio of each listing to its peer median. A ratio of one hundred and sixty is extreme, and a ratio of zero is suspicious. This is a general pattern for accuracy checks. Pick a trustworthy comparison group, compute the ratio, and investigate the extremes. And always flag first, delete later.
#4
Let me explain why the missing reason matters. If reviews per month is blank because the listing has no reviews, then the correct value is zero. Filling it with the average would invent reviews that never happened. If the value were blank because a form field was skipped at random, a different treatment would be right. In module three's next lecture we will see the names for these cases: missing completely at random, missing at random, and missing not at random. For now, remember to ask why before deciding how.
#5
Let me explain what this does to your analysis. Suppose you compute the average price by borough. With ten labels, the table shows lowercase manhattan as its own borough with a much smaller number of rows. Anyone reading the table would be confused, and a model would treat them as different categories. This kind of problem is easy to miss, because everything looks fine until you count the groups. Whenever you use a categorical column, print its value counts first.
#6
Let me give examples of each direction. Across rows: Delhi, delhi and New Delhi in the same column. Across columns: a price column in rupees and another in dollars, where one is just the other multiplied by a rate, and both are sometimes updated differently. Across sources: the sales team records a customer by phone number, and the finance team by account number, so the same person looks like two customers. Consistency problems are the main reason why integration is hard, which is the next topic.
#7
Let me explain the rule table idea. Each rule is a short test that returns true or false for each row, such as price greater than or equal to zero. You count the rows that fail each rule, and you look at them. Note the geographic box example. Five rows failed the rule, but they were real listings in Staten Island, outside the box we had drawn. So the rule was wrong, not the data. Validity checks therefore need a human to review the failures, and they should be documented, so that the next person knows why the rule was relaxed.
#8
Let me give a simple illustration. Imagine one file from the sales team and one from finance, both listing customers. The key may be a customer ID, but you must check that it is unique in each file, otherwise a merge will create extra rows. The schema may differ, so one file calls it cust name and another customer name, and one stores dates as day, month, year and another as year, month, day. Conflicts arise when the same customer has different addresses in the two files. You need a rule, such as the most recent source wins, and you write it down.
#9
Let me explain the merge in pandas. pd dot merge of A and B, on the key, how equals outer, indicator equals True. The indicator column called underscore merge shows left only, right only or both. That makes it very easy to see how well the sources overlap. For the matched rows, compare each field with a simple equality test. In this case, the three hundred conflicts were only differences of case, so they were not real conflicts, and the choice of which spelling to keep was easy. After resolving, drop duplicates on the key, and check the final row count against what you expect.
#10
Let me explain how to find each kind in pandas. Exact duplicates: df dot duplicated sum, and drop duplicates removes them. Same-key duplicates: df dot duplicated with subset equal to the key column and keep equal to False shows all the rows that share a key, so you can compare them. Near-duplicates: clean the text by lowercasing and removing punctuation, then group by the cleaned fields, or use fuzzy matching with a library such as rapidfuzz, and review the matches by hand. Never delete near-duplicates automatically, because two different people can have similar names.
#11
Let me explain the order of steps. After you fix the borough spelling, some rows that looked different now look the same, and they are new exact duplicates. If you had removed duplicates before standardising, those would have remained. So a good order is: strip and standardise text first, then remove duplicates, then audit again. In pandas, str dot strip, str dot lower or str dot title, and replace with a dictionary, do most of the work. For a mapping, keep the dictionary in your notebook, because it is part of the documentation.
#12
Let me explain why a rule table is valuable. When new data arrives next month, you do not want to repeat your thinking. You run the same rule table, and it tells you at once what is broken. This idea is called data validation, and there are libraries such as pandera and Great Expectations that formalise it. For this course, a simple data frame of rules and a loop is enough. The principle is the same: write the rules once, run them on every load, and treat a failure as something to investigate, not to ignore.
#13
Let me explain the documentation step, which students often skip. Keep a short change log: how many rows you started with, how many you removed and why, which values you changed, and how many rows you ended with. For example, forty nine thousand eight hundred ninety five rows in, seven hundred exact duplicates removed, three hundred case fixes applied, forty eight thousand eight hundred ninety five rows out. A reader who sees this trusts your work, and you can reproduce it months later.
